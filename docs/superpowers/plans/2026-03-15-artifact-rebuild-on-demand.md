# Artifact Rebuild-on-Demand Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enable artifacts to survive sandbox expiration by storing source files durably and rebuilding sandboxes on demand when users revisit expired artifacts.

**Architecture:** Add a `sourceFiles` JSONB column to `artifactRevisions` to persist the full source map (`Record<string, string>`) alongside each revision. Introduce a `rebuild` action in the artifacts API that creates a fresh E2B sandbox from stored source. Update the workspace UI to detect expired/dead sandboxes and offer a "Rebuild" button instead of a broken iframe. The rebuild path reuses the existing `createSession` → `writeFiles` → `startPreview` pipeline from `orchestrateCreate`.

**Tech Stack:** Drizzle ORM (PostgreSQL migration), E2B SDK, Next.js App Router (route handler), React 19

```typescript
/**
 * Load the latest revision for an artifact, including source files.
 * Used by rebuild-on-demand to reconstruct expired sandboxes,
 * and by orchestrateUpdate to merge partial file deltas.
 */
export async function loadLatestRevisionWithSource(
  artifactId: string,
  userId?: string | null
) {
  return withOptionalRLS(userId ?? null, async tx => {
    const [revision] = await tx
      .select()
      .from(artifactRevisions)
      .where(eq(artifactRevisions.artifactId, artifactId))
      .orderBy(desc(artifactRevisions.createdAt))
      .limit(1)
    return revision ?? null
  })
}
```

- [ ] **Step 4: Add sourceFiles to orchestrateUpdate revision append (MERGED, not partial)**

**Critical:** `orchestrateUpdate` receives only the _changed_ files from the model, not the complete source tree. The tool schema says "Only include files that changed" and the system prompt reinforces "do not resend unchanged files." Storing `validation.files` alone would produce an incomplete revision. We must merge the update delta with the previous revision's stored `sourceFiles`.

**Known limitation -- file deletion:** This merge can ADD and OVERWRITE files but cannot DELETE them. If the model stops using `src/OldComponent.tsx`, that file persists in `mergedSourceFiles` forever (carried forward from the previous revision). This is acceptable because:

- Orphaned files do not affect the running app -- Vite tree-shakes unreferenced modules
- Storage cost is negligible (a few KB per orphaned file in JSONB)
- The live sandbox has the same behavior: `applySourceUpdate` writes changed files but never deletes old ones
- Adding a deletion mechanism (e.g., `null` sentinel values) would require changes to the Zod schema, system prompts, validation layer, and E2B runtime -- disproportionate to the benefit
- If this becomes a real problem later, a future enhancement can add `deletedFiles?: string[]` to the update tool schema without breaking the merge logic here

In `lib/artifacts/orchestrate.ts`, in the `orchestrateUpdate` function, **before** the `appendArtifactRevision` call (around line 565), load the previous revision and merge:

```typescript
// Load previous revision's source files so we can merge the delta.
// NOTE: This merge is additive-only -- it cannot represent file deletions.
// If the model removes a file by no longer importing it, the file content
// persists in the stored revision. This is harmless: Vite tree-shakes
// unreferenced modules, so orphaned files don't affect the running app.
// The live sandbox has the same behavior (applySourceUpdate never deletes).
const previousRevision = existing.artifact.currentRevisionId
  ? await dbActions.loadLatestRevisionWithSource(
      existing.artifact.id,
      ctx.userId
    )
  : null

// Merge: previous full source + current update delta = new full source
const mergedSourceFiles = {
  ...(previousRevision?.sourceFiles ?? {}),
  ...validation.files
}

const revision =
  ctx.userId && ctx.triggeringMessageId
    ? await dbActions.appendArtifactRevision(
        {
          artifactId: existing.artifact.id,
          triggeringMessageId: ctx.triggeringMessageId,
          promptSummary,
          title,
          sourceFiles: mergedSourceFiles // <-- MERGED full source tree
        },
        ctx.userId
      )
    : null
```

## Chunk 2: Rebuild Engine — Core Server Logic

### Task 4: Create `rebuildArtifactFromRevision` function

**Files:**

- Modify: `lib/db/actions.ts` (add `claimArtifactForRebuild`)
- Create: `lib/artifacts/rebuild.ts`
- Create: `lib/artifacts/rebuild.test.ts`

This is the core rebuild function. It takes an artifact ID, loads the latest revision's source files, creates a fresh sandbox, writes files, starts preview, and updates the DB.

**Concurrency safety:** Two simultaneous rebuild requests could create two E2B sandboxes, with one orphaned when the DB upsert overwrites the other's session. To prevent this, we use optimistic locking: an atomic `UPDATE ... WHERE status != 'building'` claims the artifact for rebuild. Only the first request proceeds; the second gets a 409 response. No schema migration needed — reuses the existing `'building'` status.

- [ ] **Step 1: Add `claimArtifactForRebuild` to `lib/db/actions.ts`**

This is the concurrency guard. It atomically transitions the artifact status to `'building'` only if it is not already building. If two concurrent rebuild requests race, only one gets a non-null return; the other gets null and should bail out.

In `lib/db/actions.ts`, add after `updateArtifactRecord` (around line 315):

```typescript
/**
 * Atomically claim an artifact for rebuild by transitioning its status
 * to 'building', but only if it is not already building.
 *
 * Returns the updated artifact if the claim succeeded, or null if
 * another rebuild is already in progress. This prevents concurrent
 * rebuild requests from orphaning E2B sandboxes.
 */
export async function claimArtifactForRebuild(
  artifactId: string,
  userId?: string | null
) {
  return withOptionalRLS(userId ?? null, async tx => {
    const [artifact] = await tx
      .update(artifacts)
      .set({ status: 'building', updatedAt: new Date() })
      .where(
        and(
          eq(artifacts.id, artifactId),
          sql`${artifacts.status} != 'building'`
        )
      )
      .returning()

    return artifact ?? null
  })
}
```

Note: `and` and `sql` are already imported. No new imports needed.

Create `lib/artifacts/rebuild.ts`:

```typescript
import { createE2BRuntime } from '@/lib/artifacts/runtime'
import { logArtifactEvent } from '@/lib/artifacts/observability'
import { getTemplateId } from '@/lib/artifacts/runtime/e2b-runtime'
import * as dbActions from '@/lib/db/actions'

type RebuildInput = {
  artifactId: string
  userId: string | null
  /** For guest users — the sandboxId from the guest token for session continuity */
  guestSandboxId?: string
}

type RebuildResult =
  | {
      success: true
      previewUrl: string
      sandboxId: string
      runtimeSessionId: string
      status: 'ready'
    }
  | {
      success: false
      error: string
      /** When true, another rebuild is already in progress — not a real error. */
      alreadyInProgress?: true
    }

/**
 * Rebuild an artifact sandbox from the latest stored revision.
 *
 * Used when a user revisits an artifact whose E2B sandbox has expired.
 * Creates a fresh sandbox, writes the stored source files, starts the
 * dev server, and updates the runtime session in the database.
 *
 * Concurrency safety: uses claimArtifactForRebuild (a conditional
 * UPDATE ... WHERE status != 'building') to ensure at most one
 * sandbox is created per artifact at a time.
 */
export async function rebuildArtifactFromRevision(
  input: RebuildInput
): Promise<RebuildResult> {
  // CONCURRENCY: Atomically claim the artifact for rebuild.
  // If another rebuild is already in progress, this returns null
  // and we bail out without creating a sandbox.
  const artifact = await dbActions.claimArtifactForRebuild(
    input.artifactId,
    input.userId
  )
  if (!artifact) {
    return {
      success: false,
      error: 'A rebuild is already in progress for this artifact.',
      alreadyInProgress: true
    }
  }

  const revision = await dbActions.loadLatestRevisionWithSource(
    input.artifactId,
    input.userId
  )
  if (!revision?.sourceFiles) {
    // Release the claim — no source files means we cannot rebuild.
    // Use 'expired' instead of 'failed' so user can retry if this was transient.
    await dbActions.updateArtifactRecord(
      { id: artifact.id, status: 'expired' },
      input.userId
    )
    return {
      success: false,
      error:
        'No source files stored for this artifact. It was created before rebuild-on-demand was available.'
    }
  }

  const runtime = createE2BRuntime()
  let sandboxId: string | null = null

  try {
    logArtifactEvent('artifact.rebuild.start', {
      artifactId: artifact.id,
      revisionId: revision.id
    })

    const session = await runtime.createSession({
      templateId: getTemplateId()
    })
    sandboxId = session.sandboxId

    const skipInstall = process.env.E2B_SKIP_INSTALL === 'true'

    // Validate stored source files before writing to sandbox.
    const { validateSourceFiles } = await import('@/lib/artifacts/validation')
    const validation = validateSourceFiles(revision.sourceFiles)
    if (!validation.valid) {
      throw new Error(`Source file validation failed: ${validation.error}`)
    }

    // With the custom template, dependencies are pre-installed — only
    // write model-generated source files. For base template, merge
    // template files first (same logic as orchestrateCreate).
    let files = validation.files
    if (!skipInstall) {
      const { readTemplateFiles } =
        await import('@/lib/artifacts/templates/read-template')
      files = { ...(await readTemplateFiles()), ...validation.files }
    }

    await runtime.writeFiles({ sandboxId, files })

    if (!skipInstall) {
      await runtime.installDependencies({ sandboxId })
    }

    const preview = await runtime.startPreview({ sandboxId })

    const runtimeSession = await dbActions.upsertArtifactRuntimeSession(
      {
        artifactId: artifact.id,
        provider: 'e2b',
        sandboxId,
        previewUrl: preview.previewUrl,
        status: 'ready',
        startedAt: new Date(),
        lastHeartbeatAt: new Date()
      },
      input.userId
    )

    logArtifactEvent('artifact.rebuild.complete', {
      artifactId: artifact.id,
      sandboxId,
      revisionId: revision.id
    })

    return {
      success: true,
      previewUrl: preview.previewUrl,
      sandboxId,
      runtimeSessionId: runtimeSession.id,
      status: 'ready'
    }
  } catch (error) {
    // Clean up the sandbox if it was created but build failed
    if (sandboxId) {
      try {
        await runtime.destroySession({ sandboxId })
      } catch {
        // Best-effort cleanup
      }
    }

    const message = error instanceof Error ? error.message : 'Rebuild failed'

    logArtifactEvent('artifact.rebuild.error', {
      artifactId: artifact.id,
      error: message
    })

    // CONCURRENCY: Release the claim by setting status to 'expired'
    // (not 'failed') so the user can retry. Only permanent errors
    // (like missing source files, handled above) warrant 'failed'.
    await dbActions.updateArtifactRecord(
      { id: artifact.id, status: 'expired' },
      input.userId
    )

    return { success: false, error: message }
  }
}
```

### Task 5: Allow expired guest tokens for rebuild auth

**Files:**

- Modify: `lib/artifacts/guest-token.ts:109-155`

**Problem:** Guest users hitting "Rebuild" have an expired token (the whole reason they need to rebuild). The current `verifyGuestArtifactToken` (line 142) rejects expired tokens: `if (Date.now() >= payload.expiresAt) return null`. This blocks guest rebuild entirely — a chicken-and-egg problem.

**Solution:** Add a `verifyGuestArtifactTokenAllowExpired` function that validates the signature but skips the time check, with a 30-day max-age ceiling. This is safe because: (a) the signature proves the token was issued by us, (b) the `artifactId` claim is still checked against the route parameter, (c) the rebuild action immediately issues a fresh token with a new expiry, (d) the 30-day ceiling prevents indefinite replay of leaked tokens.

```typescript
/**
 * Verify a guest artifact token, accepting expired tokens.
 *
 * Used exclusively by the `rebuild` action: the user's token has expired
 * (because the sandbox expired), but the signature still proves identity.
 * The rebuild handler immediately issues a fresh token after success.
 *
 * Security invariants:
 * - Signature is validated (forgery is rejected).
 * - A 30-day max-age ceiling prevents indefinite replay of leaked tokens.
 * - Only the standard time check is skipped — all other validation applies.
 * - The caller MUST check `handle.artifactId` against the route parameter.
 */
const MAX_EXPIRED_TOKEN_AGE_MS = 30 * 24 * 60 * 60 * 1000 // 30 days

export async function verifyGuestArtifactTokenAllowExpired(
  token: string
): Promise<ValidatedGuestArtifactHandle | null> {
  try {
    const secret = process.env.GUEST_ARTIFACT_SECRET
    if (!secret) return null

    const dotIndex = token.indexOf('.')
    if (dotIndex === -1) return null

    const payloadB64 = token.slice(0, dotIndex)
    const signatureB64 = token.slice(dotIndex + 1)
    if (!payloadB64 || !signatureB64) return null

    const key = await importKey(secret)
    const encoder = new TextEncoder()
    const signatureBytes = base64urlDecode(signatureB64)
    const signatureBytesForCrypto = new Uint8Array(signatureBytes.length)
    signatureBytesForCrypto.set(signatureBytes)

    const valid = await crypto.subtle.verify(
      'HMAC',
      key,
      signatureBytesForCrypto,
      encoder.encode(payloadB64)
    )
    if (!valid) return null

    const payloadBytes = base64urlDecode(payloadB64)
    const payloadJson = new TextDecoder().decode(payloadBytes)
    const payload: GuestArtifactTokenPayload = JSON.parse(payloadJson)

    // Skip the standard expiry check, but enforce a max-age ceiling.
    // Tokens older than 30 days are rejected even with valid signatures,
    // preventing indefinite replay of leaked tokens.
    if (Date.now() - payload.expiresAt > MAX_EXPIRED_TOKEN_AGE_MS) return null

    return {
      artifactId: payload.artifactId,
      runtimeSessionId: payload.runtimeSessionId,
      sandboxId: payload.sandboxId,
      chatId: payload.chatId,
      expiresAt: new Date(payload.expiresAt)
    }
  } catch {
    return null
  }
}
```

### Task 10: Detect sandbox expiration on workspace open

**Files:**

- Modify: `components/artifact/artifact-preview-frame.tsx`

Currently, when a user navigates to an old chat, the workspace opens with `status: 'ready'` from persisted message parts, but the sandbox is dead. The iframe silently fails to load. We need to detect this and transition to `expired` status.

**Concern: 15s iframe timeout is too aggressive**

A naive 15-second `setTimeout` produces false positives. E2B sandbox cold starts can take time: `Sandbox.create` has `DEFAULT_SANDBOX_TIMEOUT_MS = 300_000` (5 min), and `waitUntilPortReady` in `e2b-runtime.ts` polls for up to `PORT_POLL_TIMEOUT_MS = 30_000` (30s). Even for warm sandbox reconnection via `Sandbox.connect`, network variability on slow connections can exceed 15s.

Instead of a single timeout, use a **two-phase approach with a server-side probe**:

1. **Phase 1 (10s): "Still loading..." hint.** After 10s of the iframe not loading, show a subtle "Still loading..." message overlaid on the spinner. This manages user expectations without declaring expiration prematurely.

2. **Phase 2 (server probe): Authoritative check.** At the same 10s mark, fire a `refresh` API call to the artifact actions endpoint. The server checks the actual sandbox/session state and returns the authoritative `status`. If the server says `expired`, the workspace transitions immediately (via the `useArtifactAction` response handler which calls `updateWorkspace`). If the server says `ready`, the iframe continues loading. This is superior to a blind timeout because:
   - The server can detect dead sandboxes authoritatively (E2B returns errors for expired sandbox IDs).
   - The `refresh` action already exists and returns the current status.
   - It auto-populates `canRebuild` from the API response (from Task 8), so the rebuild button is correctly gated.

3. **Hard ceiling (30s): Fallback timeout.** If the iframe still hasn't loaded after 30s AND the server probe hasn't resolved the situation, declare expired. This aligns with the `PORT_POLL_TIMEOUT_MS` (30s) used server-side for dev server startup.

- [ ] **Step 1: Implement two-phase detection**

In `components/artifact/artifact-preview-frame.tsx`, update the component. After the existing `useState` declarations, add:

```typescript

const { state, updateWorkspace } = useArtifact()
const { execute: probeRefresh } = useArtifactAction('refresh')

// Phase 1: After 10s, show "still loading" hint and fire server probe.
// The probe calls the refresh action, which updates workspace state
// (including status and canRebuild) from the authoritative server response.
// If the sandbox is dead, the server returns status: 'expired' and the
// useArtifactAction response handler transitions the workspace automatically.
//
// Phase 2: After 30s hard ceiling, declare expired as a fallback.
// This matches PORT_POLL_TIMEOUT_MS in e2b-runtime.ts.
useEffect(() => {
  if (status !== 'ready' || !previewUrl || !isLoading) return

  let cancelled = false

  const hintTimeout = setTimeout(() => {
    if (!cancelled && isLoading) {
      setLoadSlow(true)
      probeRefresh()
    }
  }, 10_000)

  const ceilingTimeout = setTimeout(() => {
    if (!cancelled && isLoading) {
      updateWorkspace({ status: 'expired' })
    }
  }, 30_000)

  return () => {
    cancelled = true
    clearTimeout(hintTimeout)
    clearTimeout(ceilingTimeout)
  }
}, [status, previewUrl, isLoading, updateWorkspace, probeRefresh])

// Reset slow-loading state when previewUrl changes (rebuild/refresh)
useEffect(() => {
  setLoadSlow(false)
}, [previewUrl])
```
